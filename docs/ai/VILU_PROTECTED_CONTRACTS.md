## Authentication / security protected contracts (added 2026-09-06, Phase 47 audit; last updated 2026-09-06 after production deployment, commits `080874b` + `6e64c68`, live on `viluresidence.net`)

Full architecture map, 7 classified findings (V1-V7), and the implementation report live in `VILU_COMPLETION_MATRIX.md` Phase 47 and that day's Phase 47 audit/implementation reports — read them before touching any authentication code in `vilu-unified.html` or `vilu-agency-portal.html`.

**Removed as confirmed-dead (2026-09-06, commit `080874b` — do not re-add without a new, real requirement):** the login-lockout/attempt-tracking/audit-log system and SHA-256 helper and 2-hour session-timeout in `vilu-unified.html` (V3 — verified zero callers); the embedded legacy agency mini-login (`EMBEDDED_AGENCY_USERS`/`loadAgencyUsers`/`doAgencyLogin`/`agDoSignout`/`agShowTab`) in `vilu-unified.html` (V6 — verified its `#ag-email`/`#ag-pass` DOM dependencies never existed); the unauthenticated `vilu_agency_session` restore path in `vilu-agency-portal.html` (V4 — verified never written by any current code). The Security Log viewer (`showLoginLog()`) and its User Management button remain — untouched, unchanged behavior (it always showed "No login activity yet" before this removal too).

**Fixed (2026-09-06, commit `080874b`):** `vilu-agency-portal.html`'s `doAgencyLogin()` error messages are now uniform ("Incorrect email or password") for every failure case — previously distinguished "Email not found" vs. "Wrong password" (V5, an enumeration signal).

**Intentionally retained, do not remove without re-verifying first:**
- `firestore.rules` is the real authorization boundary (default-deny catch-all, `isAdmin()`/`isStaff()`/`isAgency()` role functions, agency data isolation via `agencyId==request.auth.uid`) — never weaken it in passing during unrelated work.
- `migrateLegacyUser()` (`vilu-unified.html`) and `migrateLegacyAgency()` (`vilu-agency-portal.html`) are one-time, self-healing legacy-credential fallbacks (V1/V2) — **the functions themselves remain intentionally retained**, even though both named bootstrap accounts (`viluresidence@gmail.com`, `agency@viluresidence.com`) are now confirmed migrated to real Firebase Auth (owner-verified via Firebase Console, 2026-09-06). This session has no way to inventory every real staff/agency account, so the fallback may still be needed for one it can't see — do not remove either function without a fresh, evidence-based reason.
- **The two named `DEFAULTS` entries' hardcoded/base64 password values were removed 2026-09-06 (commit `6e64c68`)** — provably safe once both accounts had real Firebase Auth credentials, since `authenticateUser()` always succeeds via the real sign-in call first. `loadUsers()` also now actively scrubs any stale plaintext password for these two specific emails on load. **This scrub is intentionally narrow — it must never be broadened to strip `password` unconditionally from every `USERS` record** (in `saveUsers()`/`syncAgencyAccounts()`/the `USERS_UPDATE` BroadcastChannel payload) until every real account's migration status is confirmed; `loadUsers()`'s "ensure default exists" check only looks at email presence, not password presence, so a blanket strip risks silently and permanently locking out any account that hasn't migrated yet. No built-in PMS UI shows per-account migration status — confirmed by reading `renderUsersTable()` in full.
- `migrateLegacyAgency()` now scrubs the plaintext password from every relevant localStorage key after a successful migration (added 2026-09-06, commit `6e64c68`), mirroring `migrateLegacyUser()`'s existing behavior — previously it did not, so a completed agency migration left a plaintext copy behind on that agency's own browser. Preserve this scrub in any future edit to either function.
- A second dead agency-routing path (`routeByRole('agency')` branch / `initAgencyPortal()` / `#agency-portal` in `vilu-unified.html`, V7) was traced and confirmed unreachable but was **deliberately left in place** — removing it means editing `routeByRole()`, which runs on every single successful login (admin/staff included), for a purely cosmetic gain. Don't remove it without a stronger reason than hygiene.
- Never store a real credential value in a report, log, commit message, or documentation file — report "credential present," never the value.
- Never run a full Firebase Auth export (`firebase auth:export` or equivalent) — that pulls real password hashes into a local file, a bigger and riskier action than this work warrants. A yes/no "does this account exist" question belongs to the owner/an authorized admin checking the Firebase Console directly.

## Performance findings (Phase 21, added 2026-09-06, updated after continuation pass; `2aa4d04`+`4605344` deployed to production 2026-09-06)

The Descent scroll-progress module in `vilu-website.html` (formerly an unnamed IIFE, now `vcInitDescentScrollProgress()`) is deferred to the `load` event, matching `vcInitCinematicStory()`'s existing pattern — this was found via real Lighthouse traces to be the single largest forced-reflow source on the page. **Live in production since 2026-09-06 (commit `2aa4d04`).** Do not revert this to an immediate/unconditional call without re-measuring first.

The Experiences chip's dolphin photo (`EXPERIENCES_CONFIG`'s `dolphinName` entry) points to `dolphin_pod_gallery-thumb.jpg` (360x203, ~10KB) instead of the full `dolphin_pod_gallery.jpg` (1600x900, ~109KB) — confirmed reliable via live-browser testing (plain `src`, no `srcset`). `HP_PKG_IMAGES['maldives-dream-bliss']` still correctly points at the full-resolution original — that's the large featured-package-card usage of the same source photo, never touch it to "match" the chip.

**A `srcset`+`sizes` approach on the gallery thumbnails (`vilu-residence-couple-sunset-beach-maldives.jpg` and `vilu-residence-maamigili-island-buggy-tour.jpg`) was tried and reverted (commits `4605344` then `f264aa3`) — do not re-attempt this without first understanding why it failed.** Live-browser testing found the browser's own `srcset`-candidate-selection-and-fetch mechanism intermittently left the `<img>` in a genuinely "broken" state (confirmed via `drawImage` throwing "the HTMLImageElement provided is in the 'broken' state") for the smaller candidate — even though the exact identical file loaded perfectly every time via a plain `<img src>` (confirmed both by direct browser navigation and a bare `new Image()` test), and `curl` confirmed the file itself was served correctly with the right `Content-Type`/byte count. The automated test suite (`phase12-preservation.test.js`) does NOT catch this class of bug — only real, live-browser loading verified it.

**A SECOND, architecturally-different approach was tried and reverted (commit `84384ad`) — this rules out `srcset` specifically as the culprit and means the real root cause is still unknown.** Per explicit owner direction, tried a plain separate-thumbnail-file `src` (no `srcset` at all — `<img src="…-thumb.jpg">` for the thumbnail, `GA_ITEMS` unchanged for the full-resolution main-view source) for the exact same two source images. The identical "broken" `drawImage`-throwing failure recurred for the same two images. Exhaustively ruled out during this pass: byte-level file corruption (`curl`+`md5sum` byte-identical), single-tab cache staleness (fresh `tabs_close`/`tabs_create` still failed), CDN/browser cache staleness (genuine hard reload, Ctrl+Shift+R, still failed), lazy-loading-pathway specifics (forced `loading="eager"` + forced re-fetch via `src=''` reassignment still failed), stale/duplicate markup (`outerHTML` inspection clean, only one DOM element references the URL). Root cause remains genuinely unresolved. **Do not attempt a third time without new tooling** (e.g. real Chrome DevTools Protocol network/decode-error inspection, not available to this session) — blind retries of a third architecture are not warranted until there's a concrete new hypothesis to test. Both thumb files were deleted after reverting; they do not currently exist in the repo.

Two other real findings were evaluated and deliberately NOT acted on — don't attempt either without a fresh reason: (1) hero video re-encoding — the local encoder (libopenh264, no perceptual rate control) cannot safely reduce either hero file's size further without risking visible quality loss; (2) consent.js/analytics.js/theme.js script loading order — their real *scripting* cost is only a few ms each, and changing load order risks the protected consent-before-analytics guarantee for an unproven benefit.

**Firestore Listen/channel long-polling — investigated, root-caused, and closed out (this is no longer an open finding requiring further work).** The homepage's Firestore SDK maintains a continuous WebChannel "Listen/channel" long-polling connection (~43-80 tiny ~50-byte requests per page load, confirmed present in the very first pre-fix baseline run, so not introduced by any session change). Confirmed via full-text search that the app's own code never calls `.onSnapshot()` anywhere in `vilu-website.html` — every Firestore call is a one-time `.get()`/`.set()`/`.runTransaction()`. Confirmed structurally (not just empirically) that exactly one Firebase app and one Firestore instance can ever exist: `ensureFirebaseReady()` calls `firebase.initializeApp()` exactly once inside `if(!fsDb){...}`, itself memoized behind `if(_firebaseReadyPromise) return _firebaseReadyPromise;`. **A prior-pass claim that this correlated with a "~5.7 second" mobile long task was investigated further this pass and retracted** — that figure came from a Lighthouse `--throttling-method=simulate` run, which mathematically models throttled-device timing from an unthrottled trace rather than measuring real execution; it is a modeling artifact, not a literal measurement. Corrective evidence gathered this pass: (a) a live, unthrottled `PerformanceObserver({type:'longtask'})` trace showed negligible main-thread activity during the actual Firestore-polling window; (b) a genuine `--throttling-method=devtools` run (real CPU throttling applied during capture, not modeled after the fact) showed a maximum real long task of 860ms and a `mainthread-work-breakdown` of only ~814ms total Script Evaluation versus ~7.3s combined Style/Layout+Rendering — i.e. the page's real cost under load is its own cinematic-design rendering work, not Firestore's background network chatter. This is inherent Firestore Web SDK transport behavior (the SDK opens this stream as part of its own architecture, independent of whether the app uses real-time listeners), not a custom application bug, and not a meaningful contributor to mobile TBT. Any future transport-level tuning still touches the explicitly protected `ensureFirebaseReady()`/Firebase-loading architecture and would need its own dedicated, carefully-tested investigation and explicit owner authorization — but do not re-open this as a Phase 21 performance-blocker; there is no evidence it is one.

Mobile LCP element is not fixed/singular — confirmed via direct evidence across multiple runs/conditions that it varies between the hero poster `<img id="vc-hero-poster">` and the hero `<video id="vc-hero-video">` itself, both being legitimate parts of the same intentional, protected poster-first hero architecture (poster shows first, video mounts after `load`). Do not "fix" this variability — it reflects the deliberate design, not a bug.

**Homecoming/courtyard image (`vilu-residence-courtyard-terrace-maamigili.jpg`/`.webp`, native 900×1200) — audited for responsive breakpoint variants and found NOT SAFE to split; left untouched (2026-09-06).** Real per-breakpoint measurement of `#vc-homecoming-img` (not guessed) found the `.vc-homecoming-media`/`.vc-homecoming` `min-height:52vh`/`70vh` rules are effectively dead at nearly every measured viewport — the container's actual rendered height is instead driven by the image's own 3:4 intrinsic aspect ratio (`height ≈ width × 4/3`) filling the CSS grid row, and at some viewport-height combinations (e.g. 430×932) CSS grid's default row-stretch inflates it further beyond even that. Because of this, the *required* physical pixel width at real device DPRs already meets or exceeds the native 900px width at every tested breakpoint: 320 CSS px → 640 physical (dpr2); 375 → up to 1125 physical (dpr3, common on iPhone X-class devices); 390 → up to 1170; 430 → up to ~1290; tablet (758 CSS px measured) → up to 1516 at real iPad dpr2 (this session's emulator caps DPR at 1 for any viewport ≥768px, a known environment limitation — real tablets are dpr2, used here); desktop at 1920×1080 already renders the image at 955×1273 CSS px even at dpr1, i.e. *larger than the native asset* before any retina multiplier. **Conclusion: creating smaller "mobile/tablet/desktop" dimension variants would upscale the image for the large majority of real users, not save bytes — do not attempt dimension-based responsive derivatives for this image without a layout change that actually shrinks its displayed size first (out of scope for Phase 21, which must preserve composition).** Separately, no local WebP encoder is available in this environment (the local ffmpeg build has no libwebp support, confirmed via `-encoders`; no local Python/Pillow either) to safely test a same-dimension, lower-quality WebP re-encode of the file actually served to capable browsers (confirmed via `currentSrc` that WebP is what loads here) — a JPEG-only re-encode test (via ffmpeg's `mjpeg` encoder, same 900×1200 dimensions) showed only ~2-20% savings depending on quality setting, and JPEG is the rarely-served fallback, not the primary served asset, so this was not shipped. **`convert` on this Windows environment resolves to the OS's FAT→NTFS disk-conversion utility, not ImageMagick — never invoke it on an image file.**

Remaining image-delivery opportunity (~682 KiB after the ~99KB dolphin fix, mostly `whale_shark_2_gallery`'s protected Below South Ari usage and `courtyard-terrace-maamigili`'s Homecoming panel) is real but not implemented — the former is already reasonably sized for its actual (large, protected) display context; the latter would need a proper breakpoint-matched responsive rebuild plus full visual QA, which didn't fit this pass's scope.

## Firebase / performance protected contract

`ensureFirebaseReady()` — memoized single shared promise, times out, allows retry after failure, loaded via dynamic non-blocking script injection started immediately (not gated on `DOMContentLoaded`). Every Firestore-touching function must `await ensureFirebaseReady()` before its first `fsDb.*` use. Opening the booking UI (popup/full page) must have zero Firebase dependency — both read only the already-loaded `ROOMS` array. Preserve this architecture (Phase 13B-2) unless a tested, explicitly-approved superior replacement is presented.

## Deployment safety rules (permanent)

- Never deploy from a scratch/temporary Firebase config.
- Never deploy from the dirty primary worktree (`C:\Users\hp\vilu-residence`).
- Never reset or clean unrelated primary-worktree changes.
- Always use a clean, dedicated, exact-commit worktree as the deploy source — verify `firebase.json`, `.firebaserc`, the Hosting site name, and the deploy source directory every single time, never assume from a prior session.
- Visual/public releases are **Hosting only** unless backend deployment is separately, explicitly authorized. Never let a deploy command accidentally include Firestore rules, Firestore indexes, Storage, or Functions.
- Fast-forward-only integration to `main`: no squash, no rebase, no cherry-pick, no force push. Verify the exact target SHA via a fresh `git fetch` + `git rev-parse`, never trust push output alone.
- A historical incident (scratch Firebase config / wrong public-root → production 404) is the reason this section exists as a hard rule, not a suggestion.

## Guest Account / CRM security contract (Phase 26 — applies once that phase begins)

## Weather/time fallback contract (Phase 6 — applies once that phase begins)

Weather/time data must load asynchronously and must never block hero rendering, LCP, booking, Firebase, consent, or main content. If the weather API fails, the website must remain beautiful with a graceful fallback (e.g. "Maamigili · South Ari — Local Time" only) — never show `undefined`, `NaN`, a broken icon, a fake `0°C`, or an empty large panel.
